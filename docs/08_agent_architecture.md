# OwlPath Agent 架构、执行轨迹与双语输出

架构契约：`owlpath.architecture.v1`  
当前执行图：`owlpath.execution-graph.v4`  
当前轨迹：`owlpath.trace.v2`  
状态：可运行开发研究版，不是医疗器械

## 1. 网页为什么展示两套架构

“Agent 架构”页面 `#/architecture` 明确分开：

1. **当前可运行架构**：仓库今天实际创建、调用和持久化的节点；
2. **完整目标架构**：未来研究路线，包括尚未实现或尚未经过验证的模型。

节点成熟度分为“已实现、部分实现、规划中”。目标图里的原始 CT 多模态模型、患者级生成式世界模型、动态贝叶斯先验、Conformal/OOD 和报告生成 Agent 不能被解释为本次已经运行。机器可读清单位于 `config/agent_architecture.v1.json`。

## 2. 当前默认：开发优先 v3

普通网页只显示开发推演入口；严格临床分支仍在后端和测试中，但由前端常量隐藏。开发模式的目的，是在纯虚构或已去标识化文本上观察完整多 Agent 链能否真实跑通。

```text
纯虚构/已去标识化病例全文
  → 快照、技术完整性预检
  → 适用性与输入质量观察
  → 稳定来源片段编译器
  → 复杂度/专病路由器
  → 5 位核心会诊 LLM 专家并行
  → 从 20 位动态专科专家中按病例证据最多召集 6 位
  → 证据委员会去重与汇总
  → 去标识化检索规划
  → 文献/相似病例检索 + 公共卫生/指南检索
  → 外部证据去重与核验
  → 病原体总诊 LLM Agent
  → 确定性 Taxonomy 与 Top-5 验证器
  → 独立审稿 LLM Agent
  → 不合格时最多一次总诊修订
  → 双语 v3 结果编译
  → 轨迹、结果和完整性哈希持久化
```

### 5 位核心会诊专家

| 角色 | 主要关注 |
|---|---|
| 感染科 | 综合感染综合征、解剖定位、宿主、暴露、微生物学、共感染和开放集候选 |
| 急诊与重症医学 | 器官衰竭、支持干预时序、非感染重症模拟病与诊断可实施性 |
| 临床流行病学 | 获得场景、地区季节、职业、水体、食物、动物、媒介和基线先验 |
| 检验医学 | 单位、趋势、分析前局限、病理生理模式与病原区分度 |
| 临床微生物与培养实验室 | 标本质量、染色/培养/分子检测、待回/阴性、污染/定植和药物对检出率影响 |

核心专家都阅读完整原文及稳定来源片段。路由器还可从放射、呼吸、消化、肝胆胰、泌尿、肾脏、神经、心血管、血液/免疫、移植、外科源控制、骨关节、皮肤软组织、妇产、儿科/新生儿、热带病/寄生虫、真菌、病毒/分子、抗菌药管理及医疗器械感染 20 个动态角色中最多选择 6 位。未选角色明确记为 `not_applicable`，不会伪造会诊意见。

### 检索、总诊和审稿

- 证据委员会先按冻结证据域与来源片段去重，不把“多个 Agent 重复一句”误当成多份独立证据。当前只核对片段 ID 是否真实存在；尚未实现“Agent 陈述必然由该片段语义支持”的独立蕴含核验，因此这一层在网页中标为“部分实现”。
- 检索规划器仅使用去标识化综合征、暴露、宿主、解剖部位和候选概念，不把病例全文发给搜索服务。
- 文献层检索 Europe PMC/PubMed 的原始研究、综述和相似病例；公共卫生层查询 WHO Disease Outbreak News 及版本化权威来源目录。WHO 未命中绝不等于没有该疾病或没有流行。
- 任一检索源失败都记录为 `retrieval_partial`，不阻断总诊；证据核验器对来源、链接和 PMID/DOI 跨库重复做确定性处理。候选特异文献当前只做题名级人体临床语境过滤，不冒充摘要或全文医学蕴含验证。
- 总诊 Agent 读取原文、专科结构化意见和文献元数据，必须生成恰好 5 个具体病原体草稿。
- 确定性验证器检查病原层级、去重、排名、来源片段引用、Agent 来源和 NCBI Taxonomy，不依赖 LLM 自我声明。
- 独立审稿 Agent 检查是否漏掉重要暴露、脑脊液/培养等待回报、影像、多器官损伤和既有治疗等事实。多 Provider 时优先使用不同模型；单 Provider 时使用独立提示词和全新上下文。
- 验证或审稿不合格时，总诊最多修订一次。修订仍不合格，只能对专科 Agent 已实际提出并通过术语验证的候选透明排序；候选不足 5 个即为技术失败，不能凭空补齐。

## 3. “Agent”与普通组件不是一回事

系统不把每个方框都包装成 Agent：

| 类型 | 含义 | 当前例子 |
|---|---|---|
| `llm_agent` | 一次有明确角色、输入和 Schema 的模型调用 | 5 位核心、0–6 位动态专科、总诊、审稿、可选修订 |
| `tool_agent` | 受限工具编排，不自由规划 | Europe PMC/PubMed、WHO DON 及候选特异证据检索 |
| `deterministic_processor` | 可重复的数据处理 | 快照、来源分段、结果编译 |
| `deterministic_validator` | 本地语义和术语规则 | Taxonomy 与 Top-5 合同检查 |
| `policy_guard` | 必须满足的技术边界 | 输入、Provider、配置和哈希完整性 |
| `observation_guard` | 只记录开发诊断 | 适用范围、输入质量、OOD/校准观察 |
| `infrastructure` | 存储与可追溯基础设施 | 运行轨迹、结果和完整性哈希 |

这些 LLM Agent 也不是有无限自主权的“AI 医生”：它们没有无限循环、任意工具权限、跨患者记忆或医嘱写回能力。

## 4. 开发与严格模式的权力边界

开发模式继续强制：

- Provider 已启用且连接测试通过；
- 输入、Provider、治理配置和执行图哈希一致；
- HTTPS/SSRF、重定向、超时、响应大小和 API Key 脱敏；
- JSON/Pydantic、Top-5、来源引用和术语合同；
- Agent 失败隔离、审计和 420 秒硬超时。

开发模式暂不把适用范围、时间不确定、OOD、校准器缺失和病例矛盾当成临床阻断；这些节点显示为观察告警，而不是绿色“临床通过”或红色“转人工”。文献检索失败也只是非阻断告警。

严格临床分支则继续执行医生复核、当前决策时点、事件可见性、外发同意、适用范围、校准/安全裁决、粒度降级和弃答。两种模式不能混为一谈。

## 5. Provider 分配和循环上限

创建运行时，后端按权重和稳定 ID 排序，冻结所有已选择 Provider：

- 5 位核心和已选动态专科专家按顺序轮转分配；
- 总诊使用最高优先级 Provider；
- 审稿优先使用第二个 Provider；只有一个时使用同一模型的新上下文；
- 单 Agent 技术失败时，最多换下一个可用 Provider 一次；
- 核心与已选动态专病 Agent 并行执行；
- 正常无重试为 7–13 次 LLM 调用，发生修订再增加 1 次；
- 整次开发运行硬超时为 420 秒。

故障转移属于技术容错，但不能无限增加费用：主调用、备用 Provider 尝试和单次修订共享同一个运行级原子计数器。专科阶段上限为 12 次 Provider 请求，整次运行上限为 18 次，以保留总诊、审稿和修订容量。预算用尽后不再外呼；轨迹保存每个真实请求的全局序号、节点尝试次数和最终 Provider。

这些数字是开发防失控限制，不是临床性能证明。“链路能跑通”、“Schema/Top-5 合同通过”与“达到中高年资医生水平”是三件不同的事；后者仍需多中心、时间/地区外部验证和前瞻性静默运行。

## 6. 来源片段和证据链

原始全文是开发推理的主要依据。本地整理器只辅助索引、时间标记和矛盾发现，不能因为抽取遗漏而删除原文中的暴露、脑脊液、肝脓肿可能、培养待回或当前抗菌药。

来源编译器按句段生成稳定 `source_fragment_id`。每个最终候选必须至少引用一个真实来源片段，并记录：

- 支持和反对证据；
- 为什么进入当前排名；
- 最大不确定性；
- 哪些专科 Agent 提出；
- 可用时对应的联网文献元数据。

轨迹只保存结构化专业意见和安全摘要，不保存模型隐藏思维链。

## 7. 运行轨迹

每个新运行冻结完整 DAG。每个 `run_execution_node` 至少记录：

- 稳定节点 key、类型、角色、依赖和版本；
- `pending / running / completed / failed / skipped` 状态；
- 业务结果和非阻断告警；
- 开始、完成、耗时和尝试次数；
- Provider、模型及输入输出 SHA-256；
- 脱敏结构化输入摘要、输出、警告和技术错误。

权威接口为：

```text
GET /api/runs/{run_id}/trace
GET /api/runs/{run_id}/trace/nodes/{node_id}
GET /api/runs/{run_id}/events
```

SSE 发送 `node_started`、`node_completed`、`node_failed` 和 `node_skipped` 等后端事件，并支持事件 ID 续传。前端不能按照动画时间自行制造完成状态。

运行链接中的 ID 是唯一权威来源：

```text
#/runs/{run_id}/progress
#/runs/{run_id}/result
#/runs/{run_id}/result?tab=trace
#/runs/{run_id}/compare
```

## 8. 双语 v3 结果

`owlpath.result.v3` 的核心结构是：

```text
status: completed | completed_with_warnings | technical_failure
summary_i18n
concrete_pathogens[5]
category_overview[]
unknown_score
coinfection_hypotheses[]
next_tests[]
evidence_sources[]
agent_observations[]
warnings[]
review
fallback_mode
result_sha256
```

中英文使用同一次模型响应产生，并共享同一套排名与分数。固定术语优先从 `config/clinical_terms.zh-en.v1.json` 读取；没有可靠中文术语时保留拉丁学名并标记翻译不完整，不自行猜译。

Top-5 的值只能叫“模型分数 / Model score”，不能显示为百分比临床概率。`unknown_score` 和病原大类单独展示，不得占据 Top-5。

## 9. 完整目标三平面

目标架构仍分为：

1. **治理、安全与版本控制面**：范围契约、模型/校准器/知识库/工具注册、权限、隐私、监控、熔断和回滚；
2. **在线临床推理面**：当前时点事件账本、临床证据编译、感染/非感染与综合征路由、判别式多模态模型、患者级世界模型、动态贝叶斯先验、开放集融合、Conformal/OOD、安全裁决和医生复核；
3. **离线科学与持续改进面**：多中心标签仲裁、消融、时间/地区外验证、Agent 轨迹评测、安全红队、前瞻静默运行和人工发布评审。

最终病原标签只能用于离线评价和下一版本改进，不能回流进同一患者、同一时点的在线推演。目标架构中的规划节点必须通过验证和人工发布评审后，才能进入当前运行架构。
