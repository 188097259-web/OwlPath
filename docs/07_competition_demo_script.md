# OwlPath 竞赛演示脚本（8–10 分钟）

## 1. 评委应该记住什么

1. OwlPath 不是把整份病例只问一次聊天模型，而是一个有角色分工、结构化合同、审稿和真实轨迹的多 Agent 系统；
2. 5 位核心会诊专家固定参加，路由器再从 20 位动态专科专家中按病例证据最多召集 6 位；
3. 总诊必须给出 5 个具体病原体，确定性验证器和独立审稿不能由总诊自己兼任；
4. 每个候选可追溯到病例来源片段、提出它的 Agent 和可用文献元数据；
5. 当前是开发推演：分数未校准，观察告警不阻断，不是临床诊断工具。

## 2. 演示前准备

演示只使用纯虚构或已去标识化文本。先运行：

```bash
cd OwlPath
./scripts/doctor.sh
make test
./scripts/start.sh
```

打开 `http://127.0.0.1:8000`。在“模型与 API”页面确认：

- 至少一个真实 Provider 已保存；
- 已使用纯合成请求完成连接测试；
- Provider 状态为启用；
- 模型 ID、Provider 类型和权重正确；
- 不在投屏时展示或重新输入 API Key。

连接测试成功不等于多 Agent 运行已经成功。建议演示前另外完成一次纯合成端到端运行，并保留其 `run_id` 链接作为网络波动时的只读备份；必须如实说明它是此前的真实 API 运行，不能冒充现场即时生成。

## 3. 分钟级演示

### 0:00–0:50：先说目标和边界

**展示**：工作台顶部提示。

**讲解词**：

> 病原学检查常晚于问诊、常规实验室和影像。OwlPath 研究的是：在当前已有信息下，多个专科 Agent 能否形成具体、可追溯、可审稿的病原体 Top-5。当前是开发和竞赛原型，分数未经校准，不能用于真实患者诊断或治疗。

### 0:50–1:50：展示系统不是一个“大黑箱”

**操作**：进入 `#/architecture`，选择“当前可运行架构”。

依次指向：

- 原始病例与稳定来源分段；
- 5 位固定核心会诊专家，以及从 20 位动态专科专家中按证据最多召集 6 位；
- Europe PMC/PubMed 文献层与 WHO DON/权威来源公共卫生层；
- 总诊、确定性合同验证、独立审稿和最多一次修订；
- 双语结果、轨迹和完整性哈希。

切到“完整目标架构”，简短指出多模态模型、世界模型、动态先验和 Conformal/OOD 均标记为规划或部分实现，系统没有把路线图伪装成已运行能力。

### 1:50–3:00：粘贴开发测试病例

**操作**：回到“多专科 Agent 开发工作台”，粘贴一段明确标注为纯虚构的文本，例如：

```text
【公开纯合成测试：从零构造，未引用任何真实病例】
48岁女性，无身份信息。在虚构教学日的急诊场景中，发热、干咳和右侧胸痛三天，近六小时气短。
体温39.0℃，呼吸频26次/分，室内空气SpO2 90%。WBC 16.0×10^9/L，CRP 160 mg/L，PCT 4.0 ng/mL，Na 132 mmol/L。
胸部CT显示右下肺叶节段性实变和少量胸腔积液。未近期住院，未使用广谱抗菌药，家庭成员无类似症状。
已在用药前送两套血培养和痰培养，结果待回；尚未进行呼吸道多重核酸检测。
```

**讲解词**：

> 原文是主要推理依据，本地抽取只帮助索引和发现矛盾。系统不应因为结构化抽取漏掉内容，就丢掉“右下肺实变”“用药前送培养”“家庭成员无类似症状”或“多重核酸尚未进行”这些关键事实；也不得把“培养已送”改写为“病原已证实”。

页面会明确提示：完整文本将发送给启用且连接测试通过的模型 Provider；若选择外部 Provider，可能发生文本外传并产生费用。开发模式不选择本地透明基线来凑结果。

### 3:00–3:30：启动真实多 Agent 运行

**操作**：点击“启动多专科 Agent”。记录跳转后的 URL：

```text
#/runs/{run_id}/progress
```

**讲解词**：

> 后端现在冻结输入、Provider 分配和完整执行图。5 位核心会诊专家与按证据召集的动态专科专家并行运行；无重试的普通路径有 7–13 次 LLM 调用，修订时再增加 1 次。网页只显示后端真实事件，不用前端定时器假装节点完成。

### 3:30–5:10：解释运行轨迹

**展示**：进度页中的运行 ID、阶段时间线、模型状态和执行图。

点击不同节点，展示：

- 节点角色、Provider、模型和版本；
- 状态、耗时、尝试次数；
- 脱敏结构化摘要和警告；
- 输入输出哈希；
- 检索节点只记录泛化查询的证明和文献元数据，不向检索服务发送病例全文。

强调轨迹不显示模型隐藏思维链，也不返回 API Key 或未过滤原始响应。

真实外部调用可能需要数分钟。如果现场运行尚未完成，可以继续讲解架构，再打开演示前保存的已完成 `run_id` 备份；不要手工伪造完成状态。

### 5:10–7:00：检查具体 Top-5

**操作**：运行完成后打开：

```text
#/runs/{run_id}/result
```

逐项检查：

- 恰好 5 个具体病原体，而不是“细菌、病毒、真菌”；
- 拉丁学名、中文/英文名和 NCBI Taxonomy ID；
- `Model score` 明确不是临床概率；
- 支持证据、反对证据、入选理由和主要不确定性；
- 病例片段 ID、文献 ID 和提出候选的 Agent；
- Unknown、大类方向和共感染独立显示，不占 Top-5；
- 下一项检查说明信息价值，但不产生药物、剂量或医嘱。

如果结果是 `completed_with_warnings`，展开“开发诊断”，说明检索部分失败、Provider 切换、资料矛盾或一次修订都可以被完整记录，而不必把工程开发变成到处弃答。

### 7:00–8:00：展示每个 Agent 到底做了什么

**操作**：展开“每个 Agent 的结构化结果”。

展示关键事实、矛盾、缺失信息和候选池。然后切换到：

```text
#/runs/{run_id}/result?tab=trace
```

强调“结果摘要”和“真实节点轨迹”是两种互补视图：前者给医生读，后者给研发、质控和评委核对。

### 8:00–9:00：解释严格临床模式没有被删除

**讲解词**：

> 当前网页隐藏了严格临床入口，因为这一阶段先验证工程链路和具体候选合同。严格分支仍保留当前决策时点、医生复核、外发同意、适用范围、安全裁决、降级和弃答，并有回归测试保护。开发模式的固定 Top-5 不等于未来临床版本也必须强行给出五个病原体。

### 9:00–9:30：结束语

> 当前公开版能证明的是：在模拟 Provider 下，多专科编排、可追溯轨迹、独立审稿和合同错误发现可按预期工作。只有当现场或事先保存的真实 Provider 运行实际完成时，才能展示该次真实模型运行；不得因此概括为所有 Provider 已经兼容或稳定。我们还不能证明系统达到三甲医院医生水平。下一步需要冻结数据和当前时点定义，完成回顾性时间外验证、多中心外部验证、校准和前瞻静默运行。

## 4. 常见问题

### “是不是把病历全文发给了大模型？”

> 开发模式会把纯虚构或已去标识化全文发送给用户选择的模型 Provider，因为全文是主要推理依据；所以不能输入直接身份信息。文献搜索不同：Europe PMC 和 PubMed 只收到泛化医学查询，不收到病例全文。

### “为什么一定要五个具体病原体？”

> 这是当前开发合同，用于逼出具体候选并测试证据追溯、术语解析和审稿闭环，避免模型用“细菌”这类无信息量词逃避任务。它不是临床安全规则，也不表示五项都应采取行动。

### “模型分数是不是患病概率？”

> 不是。它只是未校准排序分数。没有目标医院、目标人群和时间外校准前，不能显示成百分比概率。

### “检索失败是否整次失败？”

> 不会。检索是补充证据，失败会记录 `retrieval_partial`。只有 Provider、Schema、完整性、术语验证或候选不足等技术问题才使开发运行失败。

### “为什么还需要独立审稿？”

> 总诊不能同时给自己批卷。确定性验证检查数量、名称、排序和引用；独立审稿检查重要病例事实是否遗漏。两者发现的问题才触发最多一次修订。

### “现在达到三甲医院医生水平了吗？”

> 不能这样宣称。必须在同一信息、同一时点和盲法条件下比较医生、系统和医生加系统，并完成外部与前瞻验证。

## 5. 现场故障处理

- 不隐瞒网络、模型、检索或后端失败；
- 不把连接测试成功说成完整运行成功；
- 不把预先保存的结果说成现场实时结果；
- 不手工补齐病原体、修改分数、删除警告或伪造轨迹；
- 若结果为 `technical_failure`，打开失败节点说明原因，再使用已标注的备用运行链接继续展示 UI；
- 如果没有任何经过验证的真实运行结果，就只展示架构和测试能力，并明确说端到端外部 Provider 仍待验证。
