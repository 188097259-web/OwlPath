# OwlPath 临床界面语言规范

> 状态：开发版 v1  
> 目标读者：首先是临床医生，其次是医学研究者和工程人员。

## 1. 两层信息原则

### 第一层：医生首屏

首先回答五个问题：

1. 系统现在在做什么？
2. 最需要考虑哪些具体病原体？
3. 为什么这样排名？
4. 还缺什么信息，下一步查什么？
5. 哪些结论只是开发阶段的模型意见？

第一层使用临床常用句式，不直接暴露原始工程状态码、缩写或实现细节。

### 第二层：工程信息

以“工程信息”或“查看技术详情”折叠展示：

- Agent 角色、Provider 和模型指纹；
- `run_id`、Schema/Trace/Graph 版本；
- 原始状态码、重试次数、耗时和依赖节点；
- SHA-256、结构化 JSON 和完整性记录。

工程信息不删除、不美化、不替换原始值；只是不与临床结论抢占首屏。

## 2. 核心词汇

| 工程或原文 | 临床主文案 | 工程副文案 |
|---|---|---|
| 推演 | 分析 | Inference |
| 多专科 Agent | 五个临床视角 | Specialist Agents |
| Agent 协作 | 多视角意见 | Agent details |
| 病原体 Top-5 | 最需要考虑的 5 个具体病原体 | Concrete Top-5 |
| Model score | 排序分（未校准） | Uncalibrated model score |
| Unknown score | 其他或未覆盖病原分数 | Open-set score |
| 观察告警 | 技术提示 | observation warning |
| 运行轨迹 | 分析过程 | Execution trace |
| 开发诊断 | 不确定性与技术说明 | Development diagnostics |
| 结果合同 | 结果格式校验 | Result contract |
| 候选池 | 该视角提出的病原体 | Candidate pool |
| 管理模型 API | 模型设置 | Model/API settings |

## 3. 状态翻译

| 原始状态 | 临床显示 |
|---|---|
| `completed` | 分析已完成 |
| `completed_with_warnings` | 分析已完成（有技术提示） |
| `running` | 正在分析 |
| `pending` | 等待分析 |
| `failed` | 本次分析未完成 |
| `passed` | 已完成 |
| `warning` | 已完成（有技术提示） |
| `demo_bypassed` | 开发阶段仅记录 |
| `skipped` | 本次未执行 |

原始状态仍保留在技术详情中。

### 失败运行的展示规则

- 运行已是 `failed` 或 `cancelled` 时，不再显示动画、“正在分析”或 100% 进度。
- `technical_failure` 不展示 Top-5、未知分数、共感染分数或模型对照；它们是不完整的中间输出，不是可解读的结果。
- 失败首屏只回答：本次是否完成、为什么未完成、用户可以做什么。
- 已返回的五个临床视角意见可作为研发记录查看；文献检索、总诊、独立复核归入“系统综合与复核”，不冒充新的临床专科。
- 原始 Provider 错误文本不进入医生界面；页面显示安全中文解释和可执行动作，原始错误码仅放在工程详情中。

## 4. 页面阅读顺序

### 病例输入页

`1. 粘贴病例全文 → 2. 确认模型与数据去向 → 3. 开始分析`

### 结果页

`1. 具体病原体排名 → 2. 综合判断摘要 → 3. 建议优先补充的检查 → 4. 支持/反对证据 → 5. 多视角意见 → 6. 工程轨迹`

### 系统说明页

`1. 医生可读的六步分析流程 → 2. 每步为什么需要 → 3. 当前已实现/未实现 → 4. 节点、版本、依赖和哈希`

## 5. 禁用写法

- 不将“分析已完成”写成“诊断已完成”。
- 不将未校准模型分数写成概率、风险或置信度。
- 不用“已通过”暗示经过临床验证。
- 不在临床首屏直接显示 OOD、DAG、Conformal、Schema、Provider、fallback 等缩写。
- 不隐藏失败、证据缺口或原始工程状态；它们必须在第二层可查。
